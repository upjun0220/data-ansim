# Claude Code 작업 프롬프트 — V10 코드를 V11.3 설계로 전환 (2026-09-21)

저장소: `data-ansim` (현재 V10 구현, 테스트 73개 통과). 이 프롬프트는 이전 대화 없이 읽어도 되게 썼다.
설계 기준은 `1_팀공유_전체설계_V11.3_20260921.html`이다. 이 파일을 저장소 루트 `docs/`에 넣고 참고해라. 특히 "V10 대비 변경점" 표와 07-2·07-4·3-2절이 이번 작업의 명세다.
결과를 과장하지 않는 "정직한 스코핑" 원칙(README 상단)을 그대로 지켜라.

## 0. 작업 규칙

- 작업 전후로 `pytest -q tests`를 돌려라. 현재 73개 통과가 기준이다. 기존 테스트를 지우지 말고, 상권 단계 테스트는 아래 P0-1에 따라 조건부로 돌게 바꿔라.
- 코드를 고칠 때마다 `python mock_data.py --out data/mock --energy` → `python kill_criteria.py --config config/mock.json` → `python pipeline.py --config config/mock.json`이 끝까지 도는지 확인해라.
- 각 단계의 "격리 설계"(한 단계가 실패해도 다른 단계와 9단계 반출은 계속됨)를 깨지 마라.
- 위도·경도·좌표 컬럼이 든 표를 저장 거부하는 규칙(`OutputWriter`)과 소표본 억제 규칙(`output.min_cell_count`, `kepco.suppress_basis`)은 약하게 만들지 마라. 새로 만드는 표에도 똑같이 적용해라.
- KEPCO_001과 002는 합산하지 않는다는 원칙을 유지해라.
- 새 설정 키는 `config.py`의 `DEFAULT_PARAMS`와 `config/field_template.json`(설명은 `_` 접두 키)에 함께 넣고, README의 설정 표를 갱신해라.
- **P0-3(AI 예측)과 P1-2(시나리오)는 코딩 전에 설계안을 먼저 보여주고 내 확인을 받아라.** 설계안에는 함수 시그니처, 새 설정 키, 산출 표의 컬럼, 테스트 목록, 예상 작업량을 넣어라.
- 선택 패키지(`lightgbm`, `scikit-learn`, `statsmodels`)는 없어도 파이프라인이 돌아야 한다. 테스트는 `pytest.importorskip`으로 처리해라.

## 2. 작업 항목

### P0-1 — 상권 단계 비활성화와 신한카드 입력 제거

코드를 지우지 말고 끄는 방식으로 해라. 나중에 비교나 되돌리기가 필요할 수 있다.

1. `stages.commerce`(기본 `False`)를 추가해라. `False`이면 `pipeline.py`가 변화점 탐지(T_r), Outcome 축약, 이벤트 스터디, 위약 검정, 처치오염 진단(6.5), CATE(7) 단계를 건너뛰고 실행 요약에 "상권 단계 비활성(v11)"을 남긴다.
2. SHC001·SHC002가 **필수 입력이 아니게** 바꿔라. `commerce=False`이면 SHC 경로가 비어 있어도 로더·킬 크라이테리아·반입 점검이 실패하지 않아야 한다. `shc.sido` 옵션은 남겨 둔다.
3. `load_axis.py`(8단계)에서 CATE 축과 4사분면 분류를 없애고, 부하 집중도 고·저 구분과 공공 검토 유형만 낸다. `commerce=True`일 때만 기존 4사분면을 추가로 낸다.
4. CAN은 처치 정제·거점성 판별 경로를 `commerce=False`에서 쓰지 않는다. 세션 시간대 모양 `u(t)`과 공간 반복성 참고 산출은 그대로 둔다.
5. KEPCO_002는 처치시점 정의 대신 **채널 비교 표**(`s1_channel_share`)를 낸다. 법정동·시간대별 002/001 비율의 분포를 보여주되 **합산하지 마라**. 002가 없으면 이 표만 생략한다.
6. 킬 크라이테리아에서 T_r 분포 항목은 `commerce=False`일 때 "해당 없음"으로 표시한다. 활성화 창을 쓰던 원천 수록 기간 점검은 "002를 001과 대조할 수 있는 기간" 점검으로 문구를 바꾼다.
7. mock 생성기는 기본적으로 SHC 파일을 만들지 않게 하고, `--with-shc` 옵션으로만 만든다.
8. 상권 관련 기존 테스트는 삭제하지 말고 `commerce=True` 설정으로만 돌게 마킹해라.

### P0-2 — 서울 한정

1. `region.sido_prefix`(기본 `"11"`)와 `region.sido_name`(기본 `"서울특별시"`)을 추가해라. KEPCO는 지역이 텍스트라 `시도` 텍스트로, 외부 자료는 법정동·행정동 코드 앞 2자리로 거른다. 기존 `kepco.sido`와 겹치면 `region` 쪽을 우선하고 `kepco.sido`는 하위 호환 별칭으로 둔다.
2. 필터는 청크 단위로 적용해 메모리를 줄여라.
3. 시군구 폴백(`analysis_level="sigungu"`)은 서울 25개 자치구 단위가 된다. 실행 요약에 자치구 수를 남긴다.
4. mock 데이터는 서울 형태의 코드(11로 시작)와 서울 자치구 이름으로 만들어라. 법정동 수는 테스트 속도를 위해 30~60개 정도면 된다.

### P0-3 — 8-A AI 분위수 예측과 초과 위험 (먼저 설계안 보고)

`load_forecast.py`를 확장한다. 기존 4주 중앙값 함수는 이름을 `forecast_baseline()`으로 두고 비교용으로 유지한다.

**모델**
- `forecast.model`: `"auto"`(기본), `"lightgbm"`, `"sklearn"`, `"baseline"`. `auto`는 lightgbm → sklearn `HistGradientBoostingRegressor(loss="quantile")` → baseline 순으로 폴백하고, 실제 사용한 모델을 실행 요약과 킬 17번에 남긴다. sklearn은 분위수 손실을 지원하는 버전인지 확인해라.
- `forecast.quantiles`: 기본 `[0.5, 0.9]`. 분위수마다 모델을 따로 학습한다. 예측 뒤 `q90 = max(q90, q50)`로 교차를 막는다.
- **global 모델**: 서울 법정동 전체를 한 모델로 학습한다. 법정동 ID는 입력에 넣지 않는다.
- 입력 특성: 시간(0~23), 요일, 휴일유형, 전날 같은 시간 부하, 7일 전 같은 시간 부하, 같은 날의 기준 모델 값, 기온 예보(없으면 제외), 동네 특성(전기차 등록대수, 공용 충전기 수, 교정기간 평균 부하). 동네 특성은 8-C 입력에서 가져오고, 없으면 해당 특성만 뺀다.
- `random_state` 고정, 하이퍼파라미터는 학습기간 안의 시간 순 교차검증으로만 고른다. 격자는 작게(조합 10개 안팎) 둬라.

**정보 누설 방지 (테스트 필수)**
- 예측일 d의 모든 입력은 d−1일 23시 이전 값이어야 한다. 기온 예보는 발표 시각이 `weather.fcst_cutoff`(기본 d−1일 18:00) 이전인 것 중 가장 늦은 발표분만 쓴다. 이를 어기는 입력이 들어오면 예외를 내고 킬 19번을 실패로 표시한다.
- 학습·검증·평가 기간은 시간 순으로 겹치지 않게 한다. 기본은 V10과 같다: 평가 시작 전 8주가 검증, 그 이전이 학습.
- `tests/`에 누설 검사 테스트를 추가해라. 미래 값을 섞은 입력을 넣으면 실패해야 한다.

**기온 모드**
- `weather.mode`: `"forecast"`(예보 사용), `"none"`(기온 없음), `"observed"`(실측, 상한 참고용). 기본은 `"forecast"`, 예보가 없으면 `"none"`으로 폴백한다.
- 예보가 없을 때는 `"none"` 모델과 `"observed"` 모델을 둘 다 학습해 성능을 나란히 보고한다. **발표 숫자에는 `"observed"` 결과를 절대 쓰지 마라.**

**검증 산출**
- `s8a_forecast_metrics`: 전체와 법정동별로 persistence·기준 모델·AI P50의 MAE, 증가 지역 평균 오차, 피크 시간 오차, P90 적중률(실측 ≤ P90인 시간 비율), pinball loss, 검증일 수, 사용 모델, 기온 모드.
- 법정동별로 AI가 기준 모델을 못 이긴 곳은 `ai_beats_baseline=False`로 표시하고 숨기지 마라.

**급증 위험(안전 축, v11.3 정의)**
- 이 지표는 변압기 과부하가 아니라 **"그 동네의 교정기간 최대 부하 × 배율을 넘는 급증"**이다. 코드 주석, 표 제목, README에 이 정의를 그대로 써라. 코드 이름은 `surge_risk`로 한다.
- 증설 부하 `ΔL(r,h)`는 8-B가 쓰는 식(`N_new × P_rated × u(t)`)을 공용 함수로 빼서 8-A와 8-B가 함께 쓴다.
- 목표 상한 `P_target(r)`도 8-B와 같은 함수로 계산하되, **고집중도 지역만이 아니라 모든 서울 법정동**에 계산한다. 교정기간 최대 부하가 `risk.min_calib_peak_kw`(기본 1.0kW) 미만인 동네는 `not_assessed_low_load`로 표시한다.
- **점수·검증용(증설 0대, 관측 기반)**: 급증경보(r,d) = 1[max_h q̂_0.9 > P_target], 급증위험(r) = 평가일 중 경보일 비율. 실제급증(r,d) = 1[max_h L_observed > P_target]과 대조해 경보 정밀도·재현율을 낸다. 피크비율(r) = 평가일 평균 max_h q̂_0.9 ÷ 교정기간 최대 부하도 함께 낸다.
- **기준 모델 경보도 같은 방식으로** 정밀도·재현율을 계산해 AI와 나란히 둔다.
- **참고 레이어(증설 2/3/5대)**: max_h(q̂_0.9 + ΔL) > P_target인 날의 비율을 `surge_risk_with_new`로 따로 낸다. ΔL이 가정값이라 실측 검증 대상이 아니며 점수에 쓰지 않는다.
- 결과는 `s8a_risk`로 내고, 상한 배율(1.1/1.2/1.3)별로 계산한다.

### P0-4 — 8-B ESS: AI 예측 입력과 AI 효과

1. `ess.forecast_input`: `"p90"`(기본), `"p50"`, `"baseline"`. 스케줄은 이 입력으로 짠다.
2. `ess.compare_inputs`(기본 `true`)이면 **같은 사전 선정 용량**으로 baseline·p50·p90·oracle 네 입력을 모두 돌려 실측에 재현한다. 계산량을 줄이려면 비교는 기준 시나리오(증설 3대, 상한 1.2배)와 상한 1.1·1.3배에만 한다.
3. 법정동별로 `ai_effect = 1 − 초과kWh_p90 / 초과kWh_baseline`을 계산한다. 기준 모델 초과가 0이면 분모에서 빼고 대상 수를 표시한다. 과잉 방전 kWh(실측 기준으로 필요 없었던 방전량)도 함께 낸다.
4. AI 효과가 음수이거나 0 근처여도 그대로 보고한다.

### P0-5 — 8-E 두 축 결합 점수

1. `priority.axes`: 기본 `["risk", "equity"]`. `risk`는 8-A의 **증설 0대 급증위험**(`surge_risk`, 증설 시나리오 값이 아님), `equity`는 2SFCA(기존대로 접근성 낮을수록 높은 점수). 비교용으로 `["safety", "equity", "economy"]` 레거시 모드를 남겨 둔다.
2. `priority.weights`: 기본 `{"risk": 0.5, "equity": 0.5}`. 합 1, 음수 없음을 검사한다(킬 14번).
3. `priority.min_axes` 기본값을 2로 바꾼다. 결측 사유 구분(`not_assessed_*`, `data_missing`)과 순위 밖 별도 목록은 유지한다.
4. 경제성(SMP 비용 차이), ESS 미적용 초과 kWh, 증설 시나리오 급증위험(`surge_risk_with_new`)은 점수에 넣지 말고 표시 컬럼으로 낸다.
4-1. `priority.risk_metric`: `"auto"`(기본), `"surge_risk"`, `"peak_ratio"`. `auto`는 순위 대상의 50% 이상에서 `surge_risk`가 0이면 `peak_ratio`로 바꾸고 그 사실을 실행 요약과 킬 21번에 남긴다.
5. AHP 입력 처리는 두 축에서 의미가 없으므로 기본 경로에서 뺀다. 레거시 모드에서만 동작하게 둔다.
6. 민감도 격자는 `w_risk ∈ [0.35, 0.65]`로 바꾼다. 강건 상위군·경계선 계산은 순위 대상 안에서만 한다.
7. 두 축의 피어슨·스피어만 상관을 실행마다 보고한다. 기존 `axes_redundant` 경고는 레거시 모드에만 남긴다.
8. 킬 15번의 대응 문구를 "축별 순위표 2장"으로 바꾼다.

### P1-1 — 외부 입력 로더: 기온과 공휴일

1. **기온**: `paths.weather` CSV를 읽는 `weather_loader.py`. 정규화 컬럼은 `timestamp,station_or_grid,temp_obs_c,temp_fcst_c,fcst_issued_at`(KST)이다. 결측 시간은 보간하지 않는다. 서울은 관측 지점이 적어 사실상 서울 공통 기온일 수 있으니, 법정동 배정은 가장 가까운 지점 또는 격자로 하고 지점이 하나면 전체에 같은 값을 쓴다.
2. **공휴일**: `config/holidays.yaml`을 읽는 로더. 형식은 `{날짜: {type: ..., public_holiday: true/false, name: ..., source: ...}}`이다. 휴일유형은 `holiday`(단일 공휴일), `long_holiday`(3일 이상 연휴), `pre_post_holiday`(연휴 전날·다음날)로 나누고 기준은 설정으로 둔다. 파일이 없으면 기존처럼 "공휴일 미보정"으로 진행한다. **휴일을 규칙으로 임의 생성하지 마라.**
3. `tools/fetch_holidays.py`를 만들어라. 한국천문연구원 특일 정보 API(공공데이터포털 15012690)로 연도별 공휴일을 받아 위 yaml로 저장하는 스크립트다. 서비스키는 환경변수로 받는다. 이 스크립트는 인터넷이 되는 곳에서 미리 한 번 돌리는 용도이며, 안심구역 파이프라인에서는 호출하지 않는다.
4. mock 생성기에 기온(실측과, 약간의 오차를 넣은 예보), 공휴일 yaml, 기온과 요일·휴일에 반응하는 충전 부하를 추가해라. 부하에 완만한 증가 추세도 넣어라. **mock에서 AI가 기준 모델을 이기더라도 그것은 성능 근거가 아니다.** README와 실행 요약에 그렇게 적어라.

### P1-2 — 8-F 충전 부하 시나리오 (먼저 설계안 보고)

새 모듈 `load_scenario.py`. 입력이 없으면 생략하는 선택 단계다.

1. **입력**: 서울 행정동별 전기차 등록 월별 이력(OA-21236 형식, `paths.ev_history`). 행정동→법정동 매핑은 8-C가 쓰는 방식을 재사용하고, 매핑 실패율을 보고한다(킬 20번).
2. **보급 추세**: 기준월 `scenario.base_month` 이전 36개월의 연평균 증가율 g(r).
   `EV_Y(r) = EV_now(r) × (1 + k·g(r))^(Y − Y0)`, `Y ∈ {2028, 2030}`. `Y − Y0`는 월 단위로 계산해 소수 연도로 쓴다(기준월이 2026-06이면 2030년 말까지 4.5년).
   - 저: `k = 0.5`, 중: `k = 1.0`
   - 고: `k_goal`. **서울 전체의 증가 배율이 전국 목표 배율과 같아지는** k를 이분법으로 찾는다.
     `Σ_r EV_2030(r) / Σ_r EV_now(r) = m_goal`, `m_goal = goal_national / national_base`
     이 방식은 "서울의 전국 비중 유지" 가정과 같고, OA-21236 서울 합계와 국토교통부 서울 값의 정의 차이에 영향받지 않는다.
   - 설정 기본값(아래 값으로 채워 넣어라):

     | 키 | 값 | 출처·비고 |
     |---|---|---|
     | `scenario.base_month` | `"2026-06"` | 아래 전국 값의 기준월. `EV_now(r)`도 OA-21236의 2026-06 값을 쓴다(OA-21236은 2026-08까지 있으나 전국 값과 기준월을 맞춘다) |
     | `scenario.goal_national` | `4200000` | 제1차 국가 탄소중립녹색성장 기본계획의 2030년 전기차 누적 보급 목표 |
     | `scenario.national_base` | `1095218` | 2026년 6월 전국 전기차 등록대수(국토교통부 자동차 등록현황, 연료별). 국토교통부 6월 말 누적등록 보도자료의 "전기 1,095천대"와 일치 확인 |
     | `scenario.seoul_base` | `118967` | 2026년 6월 서울 전기차 등록대수(2차 출처 DataFact, 원자료 미대조). 계산에는 쓰지 않고 점검용 |
     | (계산값) `m_goal` | 약 3.835 | 4,200,000 ÷ 1,095,218 |

   - `seoul_base` 점검: OA-21236의 2026-06 서울 합계와 `seoul_base`가 5% 넘게 다르면 실행 요약에 경고를 남긴다(정의 차이 가능성, 계산은 계속).
   - `goal_national`이나 `national_base`가 비어 있으면 고 시나리오만 생략한다.
   - 전국 값은 국토교통부 보도자료로 대조했다. 서울 값은 보도자료에 시도별 수치가 없어 대조하지 못했으며, 계산에 쓰지 않으므로 결과에는 영향이 없다. 통계누리에 2026년 8월 자료까지 올라와 있으므로, 팀이 원자료 xlsx를 받으면 기준월을 2026-08로 옮겨도 된다(그때는 세 값과 `EV_now(r)`의 월을 함께 바꾼다)고 README에 적어라.
3. **탄력성 β**: 동네 간 로그-로그 회귀 `log(대표 부하) ~ log(전기차 대수)`. 대표 부하는 평가기간의 평일 저녁 피크 기준 P90 날의 일 최대 부하로 한다. 부트스트랩이나 OLS로 95% 신뢰구간을 낸다. 구간이 0을 포함하거나 β가 설정 범위(`scenario.beta_bounds`, 기본 `[0.3, 2.0]`) 밖이면 β=1로 두고 0.8·1.2 민감도로만 보고한다.
4. **부하 스케일링**: `L_Y(r,h) = L_typ(r,h) × (EV_Y(r) / EV_now(r))^β`. **8-A의 트리 모델로 외삽하지 마라.** 트리 모델은 학습 범위 밖에서 평평해지기 때문이다.
5. **판정**: 현재 상한 `P_target(r)`(1.1·1.2·1.3배)을 넘는 동네 수, 필요한 ESS 후보 용량의 변화(8-B 후보 격자 재사용), 지표 1의 미래값(충전기 수는 현재 유지 가정). 산출 표 `s8f_scenario`와 중 시나리오 2030 PNG를 낸다. 고 시나리오에서만 추가로 넘는 동네는 별도 표시한다.
6. 표와 그림 제목에 "시나리오(예측 아님), 충전기 추가 설치 없음 가정"을 반드시 넣어라.

### P1-3 — 9-H 발표 숫자 재정의

`headline.py`의 `s9_headline`을 다음처럼 바꾼다. 각 숫자 옆에 가정(증설 대수, 상한 배율, 이용률 배율, 기온 모드, 사용 모델)을 찍는다.

- 숫자 1: 충전기 1기당 전기차 대수의 지역 간 배수(기존 그대로).
- 숫자 2: 증설 0대 급증 경보의 정밀도·재현율(AI 대 기준 모델)을 먼저, 그다음 AI 효과(ESS 초과 kWh 감소율)의 법정동 평균과 범위(상한 1.1~1.3)와 대상 수. AI 예측이 실행되지 않았거나 킬 18번이 실패하면 "AI 개선 없음" 또는 "미실행"으로 표시한다.
- 숫자 3: 두 값을 나란히 낸다. (a) 현재: 증설 0대 급증위험이 `headline.risk_threshold`(기본 0.1, 10일에 하루 이상 경보) 이상인 동네 수(상한 1.2배). (b) 2030: 중 시나리오에서 현재 상한 1.2배를 넘는 동네 수, 괄호에 고 시나리오 값. 둘 다 "충전기 추가 없음" 기준이지만 (a)는 2025년 예측·관측, (b)는 보급 증가 시나리오다. 표에 기준을 각각 적고, 헤드라인 문구는 팀이 확정한다고 README에 남겨라.

### P1-4 — 킬 크라이테리아 갱신

코드의 번호는 설계 문서 번호와 다르다. 기존 코드 번호 다음에 이어서 추가하고, README에 "설계 문서 번호 ↔ 코드 번호" 대응표를 넣어라.

- 설계 17번: ML 라이브러리 설치 여부 → 폴백 경로 표시.
- 설계 18번: AI P50 MAE ≤ 기준 모델 MAE, P90 적중률 ≥ 80% → 실패 시 "AI 개선 없음" 표시, 숫자 2 산출 방식 변경.
- 설계 19번: 기온 예보 확보 여부와 발표 시각 검사 → 예보 없음이면 경고, 발표 시각이 컷오프 이후면 실패.
- 설계 20번: 전기차 등록 이력 매핑률, β 안정성, `k_goal` 보정 가능 여부.
- 설계 21번(v11.3): 증설 0대 급증위험이 순위 대상의 50% 이상에서 0인가 → 위험 축을 피크비율로 대체했음을 표시.
- 기존 14번(AHP)은 가중치 유효성 검사로, 15번은 두 축 기준으로, T_r 항목은 `commerce=False`일 때 해당 없음으로 바꾼다.
